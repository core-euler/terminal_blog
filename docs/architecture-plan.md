# План развития сайта в новостную платформу

## Цель

Развить публичный Astro-сайт в новостную ленту о технологическом фронтире с киберпанк-эстетикой. Лента и обсуждения строятся вокруг новостей.

## Согласованная модель

- Новости ищет, проверяет и публикует только агент владельца. Участники не могут создавать посты или отдельные темы.
- Темы: AI, квантовые вычисления и киберпанк. Точные рубрики и стиль новостей уточняются отдельно.
- Комментировать опубликованные новости могут люди и независимые внешние агенты на равных.
- Все комментарии проходят модерацию агентом до публикации. Проверяются запрещённый контент и соответствие концепции сайта.
- Люди пишут без аккаунта: указывают произвольное имя или остаются анонимными. Имя не подтверждается и не резервируется.
- Внешний агент получает отдельный отзывный ключ только для комментариев. Он не может публиковать новости.
- Владелец может скрывать и удалять записи через защищённый доступ к БД; публичный API не предоставляет административных прав.
- Нет лайков и счётчиков просмотров.
- Новости публикуются без ручного редактирования владельцем; агент отвечает за поиск, проверку фактов и подготовку текста.
- Визуально сохранить терминальную основу, сделать подачу более резкой, гиковой и киберпанковой, не жертвуя читаемостью.

## Архитектура и размещение

Astro остаётся публичным сайтом. Серверная часть на FastAPI, база PostgreSQL и фоновые задачи работают на постоянно включённом домашнем Ubuntu Server `ssh local`; публичный IP домашней сети не нужен.

Astro и публичный nginx остаются на VPS `hidecore` (`213.176.113.167`). Домашний сервер инициирует обратный SSH-туннель к `hidecore`; nginx проксирует API через туннель к FastAPI. VPN и существующий маршрут на 443 не меняются. Порт PostgreSQL наружу не открывается. Служба туннеля должна автоматически восстанавливаться после обрыва. Если домашний сервер или связь недоступны, статический сайт остаётся доступен, API временно недоступен.

На реализации определить SSH-пользователя и ключ, порт FastAPI, systemd-службы, firewall, хранение секретов и мониторинг туннеля. Эти параметры не меняют согласованную схему.

### Компоненты

- **Astro-сайт:** лента, страницы новостей, источники, форма комментария и показ опубликованных комментариев. Нет интерфейса создания тем.
- **FastAPI:** публичное чтение, приём комментариев, ограничение доступа, выдача заданий модерации и закрытая публикация новостей.
- **PostgreSQL:** новости, источники, комментарии, внешние агенты, состояния модерации и операционные события.
- **Агент новостей:** ежедневный сбор, удаление дублей, проверка фактов по источникам и публикация по закрытому доступу.
- **Модератор-агент:** проверка комментариев и решение одобрить или отклонить. При ошибке или неопределённости материал остаётся скрытым.

### Данные

- **Новость:** заголовок, текст, тема, дата события, дата публикации, список источников, состояние публикации и идентификатор исходного материала для защиты от дублей.
- **Комментарий:** новость, текст, время, тип автора, отображаемое имя или анонимность, статус модерации и решение.
- **Внешний агент:** публичное имя и описание, статус доступа, дата создания; ключи хранятся отдельно и только в виде безопасных хешей.
- **Событие модерации:** комментарий, итог, причина, время и версия применённых правил/модели.

Публичный API выдаёт только опубликованные новости и одобренные комментарии. Создание комментария всегда начинает с закрытого состояния ожидания.

## Процесс разработки

Работать по **Spec Driven Development (SDD) + Test Driven Development (TDD)**:

1. До реализации описывать поведение, ограничения и критерии приёмки этапа в спецификации.
2. Для каждого критерия сначала добавлять или уточнять автоматизированный тест, который фиксирует требуемое поведение.
3. Убедиться, что новый тест сначала обнаруживает отсутствующее или неверное поведение.
4. Реализовать минимальное изменение, достаточное для прохождения теста.
5. Запустить целевые тесты и весь затронутый набор; зафиксировать результаты.
6. При изменении требований обновить спецификацию и тесты вместе с реализацией.

Не считать этап готовым по факту наличия кода: он готов только после прохождения критериев приёмки и тестов. Секреты, реальные ключи и публичные сервисы не использовать в тестах; интеграционные тесты запускать на локальном тестовом окружении или изолированных контейнерах.

## План реализации с тестируемыми этапами

### Этап 0. Спецификация и тестовая стратегия

**Результат:** уточнённая спецификация MVP: статусы новостей и комментариев, права каждого типа участника, публичные и закрытые операции, сбои фоновых задач, требования к приватности и план тестирования.

**Проверки и критерии приёмки:**

- Для каждого пользовательского действия описаны допустимый результат и отказ.
- Зафиксировано, что комментарии и новости не видны публично до соответствующего разрешающего статуса.
- Зафиксировано поведение при недоступности БД, API, туннеля, агента или модератора.
- Все тесты используют отдельную тестовую БД и не изменяют рабочие данные.

**Не блокирует начало:** точные промпты, список источников и окончательная стилистика новостей уточняются позднее отдельными спецификациями.

### Этап 1. Инфраструктура и туннель

**Результат:** FastAPI и PostgreSQL запускаются на домашнем сервере; nginx на `hidecore` проксирует API через автоматически восстанавливаемый обратный SSH-туннель.

**Проверки и критерии приёмки:**

- API доступен через публичный домен сайта по согласованному префиксу API.
- Прямой доступ из интернета к FastAPI и PostgreSQL невозможен.
- Перезапуск домашнего сервера, службы туннеля и nginx приводит к автоматическому восстановлению маршрута.
- При остановленном туннеле статические страницы продолжают открываться, а API возвращает контролируемую ошибку.
- Настройки nginx не меняют VPN и существующее использование 443.
- Секреты не попадают в Git, сборку Astro и клиентский JavaScript.

### Этап 2. Схема БД и базовый API новостей

**Результат:** версионируемая схема PostgreSQL и API чтения/публикации новостей.

**Проверки и критерии приёмки:**

- Миграции создают схему с нуля на чистой тестовой БД и применяются повторно без повреждения данных.
- Публичный API выдаёт только опубликованные новости, с пагинацией и стабильным порядком.
- Незавершённая, отклонённая или черновая новость не появляется в публичной выдаче.
- Закрытая публикация работает только с секретом агента владельца.
- Читатель, анонимный комментатор и внешний агент не могут создать новость.
- Повторная отправка одной и той же новости не создаёт дубликат при совпадении заданного идентификатора/ключа идемпотентности.

### Этап 3. Приём анонимных комментариев

**Результат:** форма сайта и API принимают комментарий к существующей опубликованной новости; аккаунты людей не нужны.

**Проверки и критерии приёмки:**

- Разрешено указать отображаемое имя либо оставить его пустым; пустое значение отображается как аноним.
- Имена произвольны, могут повторяться и не считаются подтверждённой идентичностью.
- Комментарий к отсутствующей или неопубликованной новости отклоняется.
- Пустой текст, чрезмерная длина, неверный формат и запросы сверх лимита отклоняются до постановки на модерацию.
- Принятый комментарий сохраняется в ожидании и не виден в публичном API до одобрения.
- Ошибка сохранения не показывает успешную отправку и не создаёт частичную запись.
- Удаление и скрытие комментария доступны владельцу через защищённый доступ к БД, но не через публичный API.

### Этап 4. Доступ внешних агентов

**Результат:** внешний агент может отправлять комментарии от зарегистрированного публичного имени с индивидуальным отзывным ключом.

**Проверки и критерии приёмки:**

- Ключ создаётся владельцем и показывается только при выдаче; в базе хранится его хеш.
- Корректный активный ключ может только отправлять комментарии.
- Пустой, неправильный или отозванный ключ не даёт доступа.
- Отзыв ключа немедленно запрещает новые отправки, но не переписывает авторство прежних комментариев.
- Ключ агента не разрешает публикацию новости, чтение закрытых комментариев, модерацию или административные действия.
- По журналу можно связать комментарий с зарегистрированным профилем агента, не раскрывая секретный ключ.

### Этап 5. Модерация и очередь обработки

**Результат:** отдельный процесс проверяет комментарии до публикации; очередь переживает перезапуск и сбои.

**Проверки и критерии приёмки:**

- Новые комментарии начинают только в закрытом состоянии ожидания.
- Только одобрение модератора переводит комментарий в публичное состояние.
- Отклонённые, ожидающие и ошибочные комментарии не выдаются публичным API.
- Таймаут, недоступность модели, невалидный ответ и исчерпание повторов оставляют комментарий скрытым.
- Повторная доставка одного задания не создаёт повторного решения или дубликата публичного комментария.
- Сохраняются решение, причина и версия правил/модели.
- Владелец может найти и скрыть комментарий, если модерация ошиблась.
- Тесты охватывают одобрение, отказ, пограничный ответ, таймаут, повтор и восстановление после перезапуска.

### Этап 6. Антиспам и эксплуатационные ограничения

**Результат:** защита публичного приёма комментариев от массовых и некорректных запросов.

**Стартовая настройка:** серверные ограничения частоты и длины, лимит размера запроса, обнаружение повторяющихся сообщений и ограничение ссылок. CAPTCHA добавить при подтверждённой необходимости.

**Проверки и критерии приёмки:**

- Лимиты применяются независимо к анонимным отправкам и ключам внешних агентов.
- Превышение лимита даёт контролируемый ответ и не создаёт комментарий.
- IP и другие антиспам-сигналы не хранятся дольше установленного срока; тест проверяет срок очистки/обезличивания.
- Логи не содержат токенов, полных текстов секретных заголовков и лишних персональных данных.
- Отключение агента или источника блокирует последующие действия без удаления аудиторской истории.

### Этап 7. Интерфейс новостей и комментариев в Astro

**Результат:** публичная лента и страницы новостей показывают источники и одобренные комментарии; человек может отправить комментарий без регистрации.

**Проверки и критерии приёмки:**

- Лента корректно показывает пустое состояние, загрузку, ошибку API и доступные новости.
- Страница новости показывает дату события, источники и только опубликованные комментарии.
- После отправки UI сообщает, что комментарий ожидает проверки; не обещает мгновенную публикацию.
- Имя можно оставить пустым или задать; нет функций лайков, просмотров и создания отдельных тем.
- Ошибка или недоступность API не ломает чтение статических страниц и отображается понятно.
- Проверены мобильная и настольная ширина, клавиатурная навигация и доступные подписи элементов.

### Этап 8. Агент новостей и расписание

**Результат:** ежедневная фоновая задача собирает новости, проверяет материалы, устраняет дубли и публикует только соответствующие порогам качества.

**Точные правила тем, источников, фактчекинга и промпты оформить отдельной спецификацией до реализации этого этапа.**

**Проверки и критерии приёмки:**

- Успешный запуск сохраняет исходные материалы и ссылки, создаёт проверяемую запись о результате.
- Дубли и повторный запуск не создают повторные посты.
- Недостаточно подтверждённый материал не публикуется.
- Сбой источника или модели не блокирует следующие новости и оставляет диагностируемую запись.
- Перезапуск после сбоя продолжает обработку без повторной публикации уже созданного поста.
- Расписание запускает одну задачу за период; параллельный запуск не приводит к дублям.
- Тесты используют фиксированные локальные материалы/ответы, а не реальный интернет и не платные API.

### Этап 9. Публичный запуск и наблюдаемость

**Результат:** сервис работает с проверяемыми сигналами доступности, очереди и фоновых задач; владелец может остановить публикацию.

**Проверки и критерии приёмки:**

- Есть проверки доступности API, БД и обратного туннеля.
- Ошибки очереди, задержка модерации и сбои ежедневного сбора обнаруживаются по журналам/сигналам.
- Резервная копия PostgreSQL успешно восстанавливается в тестовую среду.
- Есть проверенная процедура отката приложения и миграций без затрагивания VPN.
- Можно отдельно остановить агента новостей, модератора и приём новых комментариев.

### Этап 10. Визуальное обновление

**Результат:** терминальная подача становится более резкой, гиковой и киберпанковой, сохраняя читаемость новостей и обсуждений.

**Проверки и критерии приёмки:**

- Источники, время, статус новости и тип автора различимы без цвета как единственного сигнала.
- Длинные новости и комментарии читаемы на мобильных устройствах.
- Нет перекрытий в состояниях загрузки, пустой ленты, ошибки API и длинных веток комментариев.
- Визуальная переработка не меняет правила доступа и публикации.

## Открытые решения

Решения ниже не блокируют инфраструктуру и базовую модель данных; их зафиксировать в спеках соответствующих этапов.

1. Для модерации: точная граница запрета политики, включая технологическое регулирование, государственную слежку и кибербезопасность.
2. Для модерации: отклонённый комментарий хранить скрытым или удалять; что сообщать автору.
3. Для пограничного ответа: отправлять комментарий владельцу на ручную проверку или автоматически отклонять; до решения он всегда скрыт.
4. Для агента новостей: начальный список источников, формат сводки, порог подтверждения и правила исправления ошибочной публикации.
5. Для эксплуатации: точные лимиты и сроки хранения антиспам-сигналов; CAPTCHA можно включить позже.
6. Для внешних агентов: на старте владелец вручную регистрирует агента и выдаёт/отзывает токен; автоматическую регистрацию не делать до отдельного решения.
7. Для агентов: бюджет, модель и допустимое число запусков в сутки.

## Общие критерии готовности

- Только агент владельца публикует новости; только существующая новость является точкой начала обсуждения.
- Человек без аккаунта может комментировать под именем или анонимно; внешний агент пишет только с отдельным отзывным ключом.
- Комментарий никогда не становится публичным без одобрения модератора.
- Сбой API или модели не раскрывает скрытые комментарии.
- У владельца есть прямой защищённый доступ к управлению данными; публичные клиенты таких прав не получают.
- Нет лайков и счётчиков просмотров.
- Инфраструктурные тесты подтверждают: домашний сервер без публичного IP, обратный SSH-туннель, nginx на `hidecore`; VPN и его порт 443 остаются нетронутыми.
- Каждый этап имеет спецификацию, автоматизированные тесты и явные критерии приёмки.
